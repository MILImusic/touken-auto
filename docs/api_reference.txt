最后更新：2026-04-04

【说明】
  - 所有端点均为 POST，附带 sword + t 参数
  - HP 准确性问题：conquest / home/index 的刀剑 HP 数据不可靠
    目前唯一能读到 HP 的端点是 party/getpartyinfo，但有上下文限制（见下）

【status 错误码】
  status=0   → 正常
  status=91  → session 失效（次日更新/重新登录），主循环已接管：
               自动调用 auto_get_token() 重新登录，然后原地重跑当前 mode
  status=97  → 服务器维护中（每周二 12:00-15:00），主循环已接管：
               自动等到 15:05，再 auto_get_token() 重新登录，原地重跑当前 mode
  其他非0值  → 各端点含义不同（见具体端点说明）

  自动恢复机制（main.py 主循环）：
    - 队列用 while+索引而非 for-in，token 失效后 retry_same_mode=True
      不递增索引，下轮 while 重跑当前 mode（不会跳到下一个 mode）
    - 重新登录成功后重置 _daily_done=False，让日常任务重跑
      （main() 内必须 `global _daily_done` 否则只是局部赋值，模块标志不变）
    - auto_get_token() 等游戏跑完 reflect 后抓稳定的 sword + fuel_csrf_token
      （抓太早会拿到 DMM 登录中间值，startup 不能重复调）
    - _sword 是 property，赋值时自动同步 httpx cookie jar（Double Submit）
    - 恢复成功后发 Telegram 通知（_send_telegram）
    - mode 1/3/10 的运行时参数（layer_id 等）首次 input 后写回 params dict，
      retry 时复用，避免凌晨无人值守时阻塞在 input

端点               | 对应页面/操作

■ home/index
  页面：本丸（首页）
  触发：登录、回本丸
  返回数据（已确认）：
    party[N].slot[N].serial_id     ← 各队槽位 serial_id（无 HP！）
    resource.charcoal/steel/...    ← 资源数量
    resource.bill                  ← 依赖札数量
    situation.conquest[N]          ← 各队出征状态（field_id, finished_at）
    situation.repair[N]            ← 修理炉状态
    badge_count.mission_achieved   ← 任务徽章数
    ev                             ← 当前活动 ID
    t                              ← 新 CSRF token
  注意：
    - 无 sword 顶层字段
    - party slot 仅含 serial_id，无 HP / fatigue / 装备数据

■ conquest
  页面：出陣準備（远征队选择）
  触发：进入远征页
  返回数据（已确认）：
    sword[serial_id].fatigue       ← 气力（注：可能不准确）
    sword[serial_id].sword_id      ← 刀种 ID（静态）
    sword[serial_id].mobile        ← 机动力
    sword[serial_id].mobile_up     ← 机动力加成
    party[N].slot[N].serial_id     ← 各队槽位
    party[N].status                ← 队伍状态（1=待机, 2=出征中）
    t                              ← 新 CSRF token
  注意：
    - 无 hp / hp_max 字段（HP 不在此端点）★ 绝对不能用 conquest 做重伤检测 ★
    - fatigue 数据可能不准，需 getpartyinfo 校验
    - 曾导致 bug：道中重伤检查误用 conquest，is_heavily_injured 永远返回 False，
      刀打完一节点继续打下一节点直到碎掉

■ party/getpartyinfo?party_no=N
  页面：部隊編成（特定队伍详情）
  触发：查看某支队伍编成
  返回数据（已确认）：
    sword[serial_id].hp            ← 当前 HP ★
    sword[serial_id].hp_max        ← 最大 HP ★
    sword[serial_id].fatigue       ← 气力（准确）
    sword[serial_id].item_id       ← 御守 ID
    sword[serial_id].equip_serial_id1~4 ← 刀装
    sword[serial_id].horse_serial_id    ← 馬
    t                              ← 新 CSRF token
  HP 准确性说明：
    ✓ 普通出阵（4-3/4-4）道中/结束后：HP 准确
    ✓ 地下城 resetsallystatus 后（战斗发生过）：HP 准确
    ? 地下城 eventsally 失败（未进入战斗）后：HP 是否准确 ← 待验证
    ? 本丸待机中（上次出阵受伤未治疗）：HP 是否反映旧伤 ← 待验证
    ✗ 本丸 sally（出阵地图页）导航后：HP 被重置为本丸值
  fatigue 准确性说明：
    ✗ 登录后立即调用（home/index 后首次 getpartyinfo）：fatigue 返回缓存值（如固定100），
      与实际气力不符。服务器需经过若干交互后才刷新。
      实测：白山吉光实际气力49，登录后 getpartyinfo 返回100。
      影响：ensure_hakusan_fatigue 在登录时读数不准，但 HAKUSAN_FATIGUE_MIN=25 阈值
      足够低，行为上不受影响。

■ party/list
  页面：部隊一覧（所有队伍列表）
  触发：查看全部队伍
  返回：text/html（无 JSON 响应体）
  用途：导航操作，不提取数据

■ sally/eventsally
  页面：地下城层入口
  参数：event_id, event_field_id, party_no, item_id, event_layer_id
        [is_continuation=1 表示继续调查]
  返回：
    status=0   → 进层成功
    status=2   → 进层失败（队长重伤 / 当日限制 / 活动未开放等）
    t          ← 新 token（注：失败时可能无新 token）
  注意：status=2 的具体原因无法从响应区分，需结合上下文判断

■ sally/eventforward?direction=0
  页面：地下城节点推进
  返回：
    status=0   → 正常
    status≠0   → 队长重伤，无法继续
    is_finish  → true 表示本层结束
    item_effect→ ≠0 为物资节点（不触发战斗）
    formation_id → 游戏推荐阵型

■ battle/battle?formation_id=N
  页面：战斗
  返回：战斗结果（HP 变化体现在后续 getpartyinfo）

■ sally/resetsallystatus
  页面：层结算（出阵结束/中途撤退确认）
  参数：无额外参数
  返回：sword+t（更新 token 和刀剑数据）
  注意：
    - 调用后进入"HP 准确窗口"（已发生过战斗的情况下）
    - 此后调用 getpartyinfo 可读到准确 HP
    - 调用 sally 等导航端点后窗口关闭

■ sally/updateautoplayflaginsally?type=3
  页面：重伤弹窗确认
  触发：检测到重伤后，对应游戏弹出的确认对话框
  返回：t

■ sally（无子路径）
  页面：出阵地图选择页
  触发：进入出阵界面
  返回：JSON（可能含 script 字段用于日常对话）
  注意：调用此端点会重置 HP 到本丸值

■ sally/sally
  操作：选择地图并出阵（进入出阵前必须先调用 sally）
  参数：episode_id, field_id, party_no（三个一起传，不可分两次调用）
  返回：t
  注意：episode_id/field_id 分别对应章节和地图编号（如 7-3 = episode_id=7, field_id=3）
        部分章节（如 episode 7）不接受缺少 party_no 的调用（500 Internal Error）

■ sally/startup
  操作：出阵初始化（sally/sally 之后调用）
  返回：history（路线信息）, t

■ sally/forward
  操作：普通出阵中前进一个节点
  参数：direction=0
  返回：
    status       ← 0=正常，≠0=队长重伤无法继续
    is_finish    ← true=最终节点
    item_effect  ← ≠0 为物资节点（无需战斗），=0 为战斗节点
    formation_id ← 始终为 None（普通出阵不提供推荐阵型）
    scout.formation_id ← 敌方阵型（0=未知，1~6=具体阵型）
    scout.enemy  ← 敌方单位 ID 列表
    t
  与 sally/eventforward 的关键区别：
    - eventforward 返回服务器推荐阵型（formation_id 有值），可直接使用
    - forward 不返回推荐阵型，需根据 scout.formation_id（敌方阵型）自行选择克制阵型
    - scout.formation_id=0 时敌方阵型未知，默认鱼鳞阵(4)

■ home/leave?serial_id=N&is_leave=0

【待验证问题】
-------------------------------------------------------------------
Q1: party/getpartyinfo 在"本丸待机"状态下能否检测到地下城遗留重伤？
    ✓ 已确认根本原因：代码 Bug，非 API 问题（见下方【已确认结论】）
    现象解释：sword 字段值中无 serial_id，旧代码用 sd.get("serial_id") 永远 None，
    导致所有刀被跳过，始终显示"全队无重伤刀"。

Q2: 重伤状态标记字段是否存在？
    △ 未完全确认。已知 sword 数据有 status 字段（值 3 出现在伤刀和满血刀），
    含义不明。当前不依赖 status 字段，仅依靠 HP ≤ 25% 判断重伤。

Q3: eventsally status=2 的真实原因？
    ✓ 根本原因已确认：HEAVY_INJURY_RATIO 阈值设低了（0.25），漏检了重伤刀。
    游戏实测重伤标准约 HP ≤ 30%（官方未公布精确值，玩家 wiki 实测约 30~31%）。
    案例：378866067 HP 13/45（28.9%），0.25 阈值 miss，0.30 阈值 hit → 治疗后可进层。
    修复：HEAVY_INJURY_RATIO 从 0.25 → 0.30，全局生效，无需特殊路径。

【已确认结论】
-------------------------------------------------------------------

■ getpartyinfo sword 数据格式（重要！）
  响应格式：sword["378866067"] = {"hp": 19, "hp_max": 56, "fatigue": 100, ...}
  ★ 键是 serial_id 字符串，值（dict）内部不含 serial_id 字段 ★
  正确迭代方式：
    for str_sid, sd in resp.get("sword", {}).items():
        sid_int = int(str_sid)  # 从键取 serial_id
  错误方式（曾导致"全队无重伤刀" bug）：
    for sd in resp.get("sword", {}).values():
        sid = sd.get("serial_id")  # 永远 None！

■ 重伤（重傷）判定阈值（2026-04-04 网络查证 + 实测确认）
  官方未公布精确值，玩家 wiki 实测约 HP ≤ 30%（部分来源写 31%）。
  案例验证：serial_id=378866067 HP=13/45（28.9%），eventsally 被拦截 → 确为重伤。
  ★ 代码中 HEAVY_INJURY_RATIO = 0.30（原为 0.25，漏检 25%~30% 区间的重伤刀）★
  伤势分级参考（实测，非官方）：
    无伤  100%
    轻伤  ≤ 90%
    中伤  ≤ 65%
    重伤  ≤ 30%（当前使用值）

■ HP 自然恢复机制
  sword 数据含 recovered_at 字段（如 "2026-04-02 00:07:11"）。
  注意：wiki 明确说明"重伤状态不会随时间自动消除"，
  recovered_at 的具体含义尚不明确（可能是装备回复或其他机制）。

■ sword.status 字段
  已知值 3 同时出现在：重伤刀（HP 14/55）和满血刀（HP 53/53）。
  当前未使用此字段做重伤判断，意义待进一步确认。

■ receive/list
  操作：打开受取箱（可按筛选条件查看）
  参数：sort_type, order, item_type, sword_type, sword, t
    - sort_type=1 默认排序, sort_type=2 按顺序排序
    - item_type=0 只看刀剑
    - sword_type=1 只看短刀
  返回：JSON（Content-Type 标记为 text/html，但实际是 JSON）
    receive          ← {serial_id: {serial_id, item_type, item_id, name, ...}}
    total_count      ← 符合筛选条件的总数
    t
  注意：receive 中的 serial_id 是受取箱内的 ID，领取后变为刀剑的 serial_id
        item_id 对应 sword_id（如 11=今剣）
        item_type=2 表示刀剑

■ receive/get
  操作：从受取箱领取刀剑
  参数：serial_ids（逗号分隔，最多100个）, sort_type, order, item_type, sword_type, sword, t
  返回：JSON
    serial_ids[]     ← 领取到的刀剑 serial_id 列表（已变为正式刀剑 serial_id）
    item             ← 当前道具库存
    resource         ← 当前资源
    is_time_over     ← 是否超时
    t
  注意：serial_ids 从 receive/list 的 receive 字段提取
        不传 serial_ids 时返回空列表（不会自动选择）

■ composition/index
  操作：打开强化/习合界面
  参数：sword, t
  返回：JSON
    composition.sword    ← 所有刀剑完整数据（含 ranbu_level, ranbu_exp, protect, rarity 等）
    composition.party    ← 队伍数据（含 slot.serial_id）
    composition.equip    ← 装备数据
    composition.artifact ← 宝物数据
    t
  注意：这是获取 ranbu_level/ranbu_exp 最可靠的端点

■ composition/union
  操作：习合（将素材刀喂给目标刀提升乱舞等级）
  参数：base_serial_id（目标刀）, material_serial_id（逗号分隔，最多30个素材刀）, sword, t
  返回：text/html（无 JSON）
  注意：每把同刀素材固定 +100 ranbu_exp
        习合后需调 composition/index 确认 ranbu_level 变化

■ 习合经验值表（2026-04-14 确认）
  每把同刀 +100 ranbu_exp（固定值，与素材等级/乱舞等级无关）
  到达乱舞 Lv7 累计所需同刀数：
    ★1：57把（5700 exp）  ★2：52把（5200 exp）
    ★3：38把（3800 exp）  ★4：24把（2400 exp）
    ★5：17把（1700 exp）

■ forge
  操作：打开锻刀界面（刀解也在此入口）
  参数：sword, t
  返回：JSON
    sword            ← 所有刀剑完整数据（同 composition/index）
    forge            ← 锻造槽状态（slot_no, finished_at, multiple[]）
    equip, party, artifact, duty, resource, bill
    t
  注意：duty 结构与 composition/index 不同：
        forge 返回 {type, horse_id1/2, field_id1/2, bout_id1/2, finished_at}
        composition 返回 [serial_id, ...]（列表）

■ forge/dismantle
  操作：刀解（销毁刀剑回收资源）
  参数：serial_id（逗号分隔，最多30个）, sword, t
  返回：JSON
    resource         ← 刀解后的资源
    item             ← 当前道具
    t
  安全约束：只刀解 protect==0 的刀，绝不碰 protect>=1
  注意：serial_id 从 forge 响应的 sword 字段中提取
        需排除编队（role_id!=0）和内番中的刀

■ 極化（kaika）sword_id 映射（2026-04-18 确认）
  極化后 sword_id = 原始 sword_id + 1，kaika_level 从 0 变 1。
  例：白山吉光 164→165，鬼丸国綱 21→22，髭切 107→108。
  习合系统需要同时映射两个 ID，否则未極化素材匹配不到極化保护刀。
  _classify_swords 和 _composition_loop 均已处理。

■ 内番（duty）与习合（2026-04-18 确认）
  内番中的刀可以作为习合目标（接收经验），只有远征中的不行。
  之前错误地跳过了 duty_sids 中的保护刀，导致在内番的保护刀永远不被喂。

■ 远征中保护刀的素材处理（2026-04-21 确认）
  远征中的刀不能习合（composition/union 返回 status=2）。
  _classify_swords 从 forge 的 party（status=2）提取远征 serial_id，
  远征中的保护刀不加入 protected_map（不尝试习合），
  但仍加入 has_protected（避免误判新刀）。
  对应素材保留在仓库不刀解，等远征回来再喂。

■ 新刀保护（2026-04-21）
  受取箱收到仓库里没有保护版本的新刀时，保留一把不刀解。
  判断逻辑：sword_id 不在 has_protected 集合中 → 保留第一把。
  has_protected 含家族所有形态（極化、特、原始），避免误判。

■ 多形态刀剣家族（2026-04-21）
  get_sword_family(sword_id, kaika_level) 返回同一刀剣的所有形态 ID。
  三层判断：
    1. SWORD_FAMILIES 硬编码（髭切 107-111、膝丸 112-115）
    2. kaika_level >= 1 → {id-1, id}（標準極化）
    3. 名字以「・極」结尾 → {id-1, id}（kaika_level=0 但确实是極化，如太郎太刀・極）
    4. 默认 → {id, id+1}（原始刀往前找極化）

■ 远征配置变更（2026-04-04）
  部隊1 移为专属治疗队后，已从 EXPEDITION_TARGETS 中删除。
  当前远征目标：队2=3-2、队3=4-2、队4=5-1、队5=5-2。
  队1（白山治疗队）永远不参与远征，空闲时也不自动出征。
  run_expedition_cycle 说明更新：仅队5空闲即发，不再含队1。

■ eventsally status=2 的处理策略（2026-04-04 确认）
  status=2 原因无法区分（重伤/日限/活动关闭），当前方案：
  1. 触发全队 getpartyinfo 检查（使用 .items() 正确迭代）
  2. 若检测到重伤（HP ≤ 30%）→ 执行治疗，归城后重试
  3. 若无重伤且连续 2 次失败 → 判定为今日上限，停止循环

■ 队伍编成约束（必须遵守，违反会丢失编队）
  1. 队长（槽1）不能直接从外部放入 — 必须先放到非队长槽再交换
  2. 移除队长（remove_sword 槽1）→ 整个队伍解散
  3. set_sword(party, 1, sid) 交换队长时：
     sid 必须已在同一队伍的其他槽位中，游戏执行交换
     但交换后原队长可能被踢出队伍而非移到 sid 的原槽位
  4. 安全的队长交换方式仍需确认 — 2026-04-22 发现两步 set_sword
     同一 ID 导致临时队长被踢出队伍的 bug

  历史事故（2026-04-22）：
    Bug 1：治疗队长重伤时，还原步骤用了两次 set_sword(同一 injured_sid)：
      第一步放到槽2 → 第二步挪到槽1 → 临时队长被踢出 → 队伍残缺 → 后续治疗失败

    Bug 2：autosetequip 验证时查的是部队1（HAKUSAN_PARTY_NO），
      但刀已经从部队1 remove_sword 移出 → getpartyinfo 查不到 → 误判装备失败
      → RuntimeError → 归还步骤跳过 → 队伍空编
      修复：验证移到 remove_sword 之前（刀还在部队1时验证）

    Bug 3：RuntimeError 导致归还步骤完全跳过，无兜底机制
      修复：加 _current_injured 跟踪 + 异常后紧急归还

■ 刀装相关约束
  - 刀装会在战斗中被打掉（正常游戏机制），长期刷图后刀装数量会减少
  - equip_snapshot 反映的是治疗前的装备状态，可能已经被打掉了部分
  - 还原刀装时 setequip 次数取决于快照中有多少非空槽位
  - 如果快照中无刀装（has_touso=False）→ 调 autosetequip 自动装备
  - autosetequip 需要刀在某个队伍中才能通过 getpartyinfo 验证
  - 长期刷图后刀装库存可能耗尽 → autosetequip 失败 → 需停止运行

■ 战斗模块重伤检测约束（必须遵守，违反会碎刀）
  所有包含实战（battle/battle）的循环必须有三层检测：
    1. 出阵前：run_repair_check(party_no) — 检查+治疗重伤刀
    2. 道中（每个非最终战斗节点后）：getpartyinfo → is_heavily_injured
       → 检测到重伤立即 break 停止出阵
    3. 队长重伤：forward status!=0 → 立即 break

  已检查通过的模块：
    - sortie.py _run_single_sortie + 7个循环 ✓
    - dungeon.py _run_dungeon_floor + 爬楼/单层循环 ✓
    - parallel_past.py _run_single_parallel_past + 循环 ✓

  不需要检测的模块：
    - practice.py 演练 — 虚拟伤害，不造成实际 HP 损失
    - battle.py run_battle_1_1 — 工具函数，调用者负责检测
    - fatigue_recovery.py — 1-1 恢复，调用者负责检测

  历史事故（2026-04-21）：
    parallel_past.py 原本缺少道中重伤检测，只检查 forward status（队长重伤），
    非队长刀重伤后继续打下一场 → 太郎太刀・極 碎刀。已修复。
    教训：新增任何战斗循环时，必须包含完整三层检测。
